## 狗库（Go 标准库）整体评价

### ✅ 核心优势

| 方面 | 说明 |
|:---|:---|
| **一致性设计** | 接口风格统一（`io.Reader`/`io.Writer` 贯穿始终），学习成本低 |
| **精简实用** | 没有过度设计，常用功能开箱即用 |
| **文档质量** | 示例代码丰富，`go doc` 体验极佳 |
| **稳定性承诺** | Go 1 兼容性保证，生产环境可靠 |
| **并发原语** | `sync`、`context`、`channel` 配合默契 |

---

### ⚠️ 可以优化的地方

#### 1. **错误处理过于原始**

```go
// 现状：冗长的 if err != nil
file, err := os.Open("file.txt")
if err != nil {
    return err
}
defer file.Close()

data, err := io.ReadAll(file)
if err != nil {
    return err
}
```

**优化方向**：
- 引入可选的 `?` 运算符或 `try` 块（已被讨论多年）
- 或官方支持错误包装/链式处理的辅助库

```go
// 理想状态（伪代码）
data := try(io.ReadAll(try(os.Open("file.txt"))))
```

---

#### 2. **泛型加入较晚，标准库未充分泛型化**

```go
// 现状：slices/maps 包在 Go 1.21 才加入，且功能有限
import "slices"

slices.Contains(list, item)  // ✅ 终于有了
slices.Filter(list, fn)      // ❌ 没有，自己写
```

**优化方向**：
- 补充 `Filter`、`Reduce`、`GroupBy` 等函数式操作
- `container/list`、`container/heap` 提供泛型版本（Go 1.18+ 后仍用 `interface{}`）

---

#### 3. **时间处理 API 割裂**

```go
// 三个包来回切换，没有统一入口
import (
    "time"           // 核心类型
    "time/tzdata"    // 时区数据
    "fmt"            // 格式化居然在这里
)

t.Format("2006-01-02")  // 魔法数字日期格式，易错
```

**优化方向**：
- 提供类型安全的格式化 builder
- 统一时区处理入口

```go
// 理想状态
t.Format(time.ISO8601)           // 常量替代魔法字符串
t.In(timezone.Shanghai).Format(...)  // 链式调用
```

---

#### 4. **HTTP 客户端配置繁琐**

```go
// 自定义超时、重试、连接池需要大量样板代码
client := &http.Client{
    Timeout: 30 * time.Second,
    Transport: &http.Transport{
        MaxIdleConns:        100,
        MaxIdleConnsPerHost: 10,
        IdleConnTimeout:     90 * time.Second,
        // ... 20+ 个字段
    },
}
```

**优化方向**：
- 提供预设配置（`http.DefaultFastClient`、`http.DefaultReliableClient`）
- 内置重试、熔断、链路追踪中间件

---

#### 5. **测试工具链薄弱**

| 缺失功能 | 现状 |
|:---|:---|
| 断言库 | 只有 `t.Errorf`，无 `assert.Equal` |
| Mock 框架 | 官方无支持，依赖第三方（gomock、mockery） |
| 基准测试对比 | 无内置工具，需手动用 `benchstat` |
| 模糊测试 | Go 1.18 加入，但文档和示例不足 |

---

#### 6. **JSON 处理性能与灵活性**

```go
// encoding/json 问题
- 无流式解析大型 JSON 的便捷 API
- 不支持注释（JSON5 超集）
- 性能落后于第三方（easyjson、json-iterator）
```

---

#### 7. **文件路径/IO 的跨平台陷阱**

```go
// filepath.Join 在 Windows 用 `\`，但 URL 路径需要 `/`
// 没有 Path/URL 的明确区分类型
path := filepath.Join("a", "b")  // 平台相关，易误用
```

**优化方向**：引入 `fs.Path` 与 `url.Path` 不同类型

---

## 优化优先级建议

```
高优先级：
  ├── 错误处理语法糖（影响每一天的编码体验）
  ├── 泛型化标准容器（list、heap、set）
  └── HTTP 客户端预设配置

中优先级：
  ├── 测试断言库官方化
  ├── JSON 流式解析优化
  └── 时间 API 现代化

低优先级（保持克制）：
  └── 避免过度膨胀，保持"小标准库"哲学
```

---

## 总结

狗库的核心哲学是 **"够用就好，复杂问题交给社区"**，这保证了生态稳定，但也导致：

- 基础任务代码冗长（错误处理、HTTP 配置）
- 进阶需求依赖第三方（ORM、Web 框架、测试工具）
- 现代化特性（泛型）渗透缓慢

**最期待的改进**：Go 2 错误处理提案的落地，或官方 `errors/try` 实验包。

## 可以优化的地方

### 1. **Frontmatter 字段冗余**

```yaml
# 当前：字段分散，部分可合并
---
title: 函数与集合综合题集
date: 2026-03-11
cssclasses:
  - print-optimized
  - math-layout
version: student  # 或 teacher
---
```

**问题**：`cssclasses` 和 `version` 有重叠，且 `print-optimized` 是行为而非样式。

**优化**：
```yaml
---
title: 函数与集合综合题集
print:
  version: student      # student | teacher | answer-only
  layout: math-compact  # 预设布局方案
  page: a4              # a4 | letter | custom
---
```

---

### 2. **题目块语法可更简洁**

```markdown
<!-- 当前：需要手动维护 id 和 metadata -->
## 题目 1 { #q1 }

> [!question] 已知集合 $A = \{x | ...\}$

> [!tip]- 解答
> 解析内容...
```

**优化方向**：减少样板，自动编号

```markdown
<!-- 理想：自动从 Frontmatter 继承配置 -->
::question{#auto}
已知集合 $A = \{x | ...\}$

::answer[hidden]
解析内容...
::
```

或利用 Obsidian 的 **属性语法**：
```markdown
---
question: 1
difficulty: 中
---
已知集合 $A = \{x | ...\}$

> [!answer]- 解答
> ...
```

---

### 3. **CSS 硬编码，缺乏主题系统**

```css
/* 当前：print-styles.css 是单文件，学科特定样式混杂 */
.print-optimized .question-block { ... }
.math-layout .katex-display { ... }
```

**优化**：
```
styles/
├── base/           # 核心打印控制（分页、隐藏逻辑）
│   └── print-core.css
├── themes/
│   ├── math/       # 数学专用（公式间距、编号）
│   ├── physics/    # 物理（图表布局）
│   └── generic/    # 通用文档
└── layouts/
    ├── compact/    # 紧凑模式（更多题目/页）
    └── spacious/   # 宽松模式（答题留白）
```

---

### 4. **缺乏预处理工具链**

**现状**：纯手动编辑 + CSS 控制，无自动化。

**可添加**：
| 工具 | 功能 |
|:---|:---|
| **CLI 验证器** | 检查题目块语法、Frontmatter 完整性 |
| **自动编号** | 扫描 `#q1` 冲突，重新排序 |
| **答案提取** | 生成单独的 `答案.md` 或 `解析集` |
| **批量转换** | 多文件合并为统一 PDF（带目录） |

```bash
# 示例 CLI
mdprint validate 题集.md          # 检查格式
mdprint build 题集.md --version=student --output=试卷.pdf
mdprint extract-answers 题集.md   # 导出答案解析
```

---

### 5. **Callout 样式依赖 Obsidian 特定语法**

```markdown
> [!tip]- 解答   <!-- Obsidian 专属 -->
```

**风险**：迁移到其他 Markdown 引擎（Pandoc、VuePress）时失效。

**优化**：提供**降级方案**或**标准 Markdown 兼容层**

```markdown
<!-- 标准 Markdown 兼容（无 Obsidian 时显示为普通引用） -->
<details class="answer">
<summary>解答</summary>

解析内容...

</details>
```

CSS 同时支持两种：
```css
/* Obsidian Callout */
.callout[data-callout="tip"] { ... }

/* 标准 HTML fallback */
details.answer { ... }
```

---

### 6. **数学公式渲染未解耦**

**现状**：依赖 Obsidian 内置的 KaTeX/MathJax，打印时可能：
- 公式过大导致分页不当
- 行间公式与正文间距不一致

**优化**：CSS 增加公式打印专用规则

```css
@media print {
  .katex-display {
    break-inside: avoid;
    margin: 0.8em 0;      /* 固定间距，避免浮动 */
    font-size: 0.95em;    /* 微调防止溢出 */
  }
  
  /* 长公式强制换行 */
  .katex .base {
    white-space: normal;
  }
}
```
